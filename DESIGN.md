# Записка о дизайне AuditEnv

> Версия 1.3 (генератор 1.2.0, протокол проверок жюри от 20.11.2026).

## 1. Идея

Эпизод — одна вымышленная компания и один отчётный период. Агент исследует записи
через узкий набор инструментов и отправляет выводы с доказательствами. Среда не
обучает модель; она даёт повторяемые взаимодействия и честную терминальную награду.

## 2. Генерация: сначала история, потом ошибки

1. **План.** По seed решается, какие ошибки и сколько будет внесено.
2. **Чистая история.** Контрагенты, счета, кредит-ноты, платежи (полные, частями, сразу за
   несколько счетов), регулярные счета на одинаковую сумму, документы на границах периода,
   операционные проводки, таблица курсов FX.
3. **Проверка чистых книг.** Дебет = кредит в каждой валюте, дебиторка по проводкам сходится
   с документами, ни один счёт не переоплачен. Результат пишется в `provenance.clean_books_checks`.
4. **Мутации.** Каждый тип ошибки — отдельный `Mutator`, который меняет историю одним
   причинным изменением и записывает, что изменено (`provenance.mutations`).
5. **Финализация.** Из записей выводится книга проводок, назначаются ID, формируются публичные
   файлы, `truth.json` (тип, затронутые ID, сумма, валюта, допустимые наборы доказательств) и
   `provenance.json`. Эталон ссылается на объекты, а не на номера строк, поэтому переживает
   переименование и перестановку.

Порядок этапов: история → курсы → проверка чистых книг → ошибки → операционные проводки,
которые добирают книгу ровно до `n_ledger_rows` (поэтому ошибка может менять число строк) →
повторная проверка баланса и сверки дебиторки после ошибок.

**Валюты.** Книга ведётся в базовой валюте, документы — в своей. Счёт пересчитывается по курсу
локальной даты проводки (выходные → последний более ранний курс), касса — по курсу даты платежа,
погашение дебиторки и кредит-ноты — по историческому курсу счёта; полное погашение снимает ровно
остаток, без копеек хвоста; разница идёт на 4900. Правила опубликованы в `policy.json`, тесты
пересчитывают каждую проводку только по публичным файлам (`tests/test_fx.py`).

Детерминизм: собственный ГПСЧ SplitMix64 с отдельными подпотоками на каждый этап, деньги —
целые минимальные единицы, курсы — десятичные строки, `Decimal` с `ROUND_HALF_UP`.

## 3. Типы ошибок

| Тип | Что меняется | Доказательство |
|---|---|---|
| `duplicate_invoice` | счёт внесён второй раз: второй документ и вторые проводки | оба документа, либо пары проводок выручки/дебиторки |
| `period_cutoff_error` | дата документа вне периода, а проводки внутри | документ + его проводка |
| `partial_payment_allocation` | платёж в документе применён к счёту полностью, а в книге — частично или никак; остаток в 2100 | документ платежа + строка 2100 (или строка дебиторки) |
| `fx_rate_error` | проводка счёта (или кассы платежа) в иностранной валюте пересчитана по курсу не той даты: срок оплаты, соседние дни, дата документа | документ + неверная проводка + строка `fx.csv` с курсом, который требует политика |

Каждый тип включается отдельно через `error_types`; количество — `n_errors`.

**Сценарии взаимодействующих ошибок** (`interactions`), каждый даёт две связанные записи эталона,
каждая доказуема сама по себе:

1. `partial_fx_boundary` — платёж в иностранной валюте пришёл в последний вечер периода, применён
   к счёту только частично **и** касса пересчитана по курсу следующего дня
   (`partial_payment_allocation` + `fx_rate_error` на одном документе).
2. `cutoff_fx` — счёт с датой следующего периода проведён в текущем **и** пересчитан по курсу даты
   документа, а не даты проводки (`period_cutoff_error` + `fx_rate_error`).

Законный двойник есть у каждого: платёж в последний вечер периода без ошибок, документы на
границах периода, выходные с курсом пятницы, переплата.

## 4. Отвлекающие случаи (не ошибки)

Платёж частями, один платёж на два счёта, переплата (остаток законно лежит в 2100), возврат через кредит-ноту, одинаковые суммы
каждый месяц, документы ровно на начале и конце периода, время в UTC, которое выглядит как
другой день, документы вне периода без проводок.

## 5. Изоляция

- Среда хранит только публичные таблицы; эталон лежит внутри `Evaluator`.
- `evaluator.py` импортирует только стандартную библиотеку и `schemas` (проверяется тестом).
- Наблюдения и `info` не содержат seed, путей, ID эталона; сообщения об ошибках ≤ 200 символов.
- В режиме `eval` награда и диагностика не возвращаются политике.
- `runner.py`: агент запускается отдельным процессом (`python -I -B`, пустая временная папка,
  очищенные переменные окружения) и общается только JSON-строками через stdin/stdout. Среда,
  оценщик и эталон живут в процессе запускателя. Таймаут 60 с, лимит строки 256 КБ; падение,
  зависание, битый JSON или EOF агента дают `truncated=true` и пустой ответ, не ломая запуск.
  `check.py` прогоняет через него случайного и «враждебного» агента и проверяет, что эталон не виден.

**ID и перестановки.** `id_scheme: "randomized"` + `id_salt` дают ничего не значащие hex-ID и
перемешанный порядок строк при той же компании; эталон и provenance перемаппятся. 20 парных
тестов проверяют, что oracle получает ту же награду и F1 (`tests/test_ids_and_runner.py`).

## 6. Сопоставление и награда

- Выводы канонизируются: списки ID сортируются, повторы ID внутри списка удаляются.
- TP: совпадают тип, `affected_ids`, валюта, сумма в пределах `amount_tolerance_minor`
  (из `policy.json`) и есть хотя бы один полный допустимый набор доказательств; лишние ID
  в доказательствах не мешают.
- Все evidence_ids должны существовать среди ID, доступных агенту (row_id, doc_id, fx ID), иначе
  вывод не сопоставляется (пример M04 протокола жюри).
- Допуск суммы τ публикуется в `policy.amount_tolerance_minor`, по умолчанию 0.
- Сопоставление взаимно однозначное и максимальное (augmenting paths), поэтому порядок выводов
  не влияет на результат; повторный вывод — FP.
- P, R, F1 и особые случаи пустого эталона — ровно по условию; награда
  `clip(2*F1 - 1 - 0.002*inspection_steps, -1, 1)`; неверная структура → −1 с записью в журнал.

## 7. Измерения базовых политик

10 train + 10 dev эпизодов: по 2 чистых и по 4 со сценариями взаимодействия в каждом сплите,
половина — со случайными ID (`python check.py`, Python 3.11, 2 CPU):

| Политика | F1 train / dev | Возврат train / dev | Шаги | с/эпизод |
|---|---|---|---|---|
| случайный исследователь | 0.20 / 0.00 | −0.61 / −1.00 | 13–23 | 0.03 |
| простая сверка | 0.54 / 0.44 | 0.05 / −0.14 | 18 | 0.03 |
| «пометить всё» | 0.00 / 0.00 | −1.00 / −1.00 | 1.5 | 0.02 |
| oracle | 1.00 / 1.00 | 1.00 / 1.00 | 0 | 0.02 |

P и R у oracle = 0.80, потому что на чистых эпизодах знаменатель нулевой и по условию P = R = 0,
а F1 = 1.

**Разбор сбоев.**
- Версия 1.3: прогон тестов по опубликованному протоколу жюри нашёл два расхождения. (1) Вывод с
  лишним несуществующим ID в evidence_ids засчитывался как TP (пример M04); исправлено, тест
  `test_M_examples_matching`. (2) В тексте ошибки среда повторяла ID, присланный агентом
  (`../private/truth.json`); утечки не было, но такой текст похож на неё, поэтому повтор убран
  (тест C20). Плюс добавлены `judge_adapter.py` и загрузка эпизода из `episode_dir`.
- Версия 1.0 (2 типа): простая сверка получала F1 = 1.00, то есть среда была слишком лёгкой.
- Версия 1.1 (+ валюты, частичный платёж, переплата): F1 простой сверки 0.62 / 0.79. Она принимает
  переплату за ошибку (FP) и указывает сумму в базовой валюте вместо валюты платежа (FN).
- Версия 1.2 (+ ошибка курса, сценарии): F1 ≈ 0.5. Ошибки курса без пересчёта по `fx.csv` не видны,
  а в сценариях простая сверка находит максимум одну из двух связанных ошибок.

## 8. Честные ограничения

- Ошибки генерируются по известным заранее шаблонам; реальные книги разнообразнее.
- Курсы FX синтетические (случайное блуждание от опорного курса), без праздников, только выходные.
- Последовательные ID оставлены как режим по умолчанию для читаемости; в открытых конфигурациях
  половина эпизодов использует `id_scheme: "randomized"` (hex-ID и перемешанные строки).
- Высокая награда в этой среде не доказывает пригодность модели для реального аудита.
- Обучение весов не проводилось; заявлений об улучшении модели нет.
